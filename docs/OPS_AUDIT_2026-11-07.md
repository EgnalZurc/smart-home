**What is NOT compromised**

- `/.env` and `/.git/config` return **302** (redirect to login), verified live with

   - consider keeping Immich tailnet-only (`tailscale serve` instead of `funnel`).

**Verification**

- `access.log` records real client IPs and banned IPs stop appearing;
- `fail2ban-client status nginx-reverse-proxy` shows the jail and banned count.

## OPS-02 — Telegram bot token leaked into INFO logs

**Evidence**

`docker logs casita-suenos` emits two lines per minute like:

```
2026-11-07 10:08:01,807 [httpx] INFO: HTTP Request: GET https://api.telegram.org/bot<REDACTED>/getUpdates?offset=0&timeout=30 "HTTP/1.1 200 OK"
```

The `<REDACTED>` segment is the live bot token (format `<bot_id>:<secret>`), written in
plain text. Root cause: `services/casita-suenos/fase3-app/src/main.py` calls
`logging.basicConfig(level=logging.INFO)`, so the `httpx` logger logs every request URL.
`_sanitize_telegram_error()` only sanitizes exception messages, not `httpx` INFO lines.

**Impact**

Anyone with access to `docker logs`, journald, backups, or future log shipping can take
control of the Telegram bot (send messages, read updates, possibly register webhooks).
The value has been exposed continuously since at least the container start (2 days).

**Suggested fix**

1. In `main.py`, silence the HTTP client loggers:
   `logging.getLogger("httpx").setLevel(logging.WARNING)` and
   `logging.getLogger("httpcore").setLevel(logging.WARNING)`.
2. Rotate the token with BotFather **after** deploying the fix, and update
   `TELEGRAM_BOT_TOKEN` in the Pi `.env` via the normal deploy path.
3. Check whether existing backups (`/home/pi/backups/`) contain old container logs with
   the token; treat those backups as sensitive.

**Verification**

```
docker logs casita-suenos 2>&1 | grep -E 'bot[0-9]+:'   # must return nothing
```

## OPS-04 — nginx cannot see the real client IP

**Evidence**

- Every access log line is attributed to `172.18.0.1` (571,261 requests) or
  `172.19.0.1` (209,242); only a handful have LAN addresses.
- `nginx.conf` and `conf.d/smart-home.conf` set `X-Forwarded-For` downstream but never
  define `real_ip_header` / `set_real_ip_from`.

Requests arrive through Tailscale Funnel, which terminates TLS and forwards to nginx on
localhost, so `$remote_addr` is the Docker gateway.

**Impact**

- Scanner IPs cannot be identified or banned (see OPS-01).
- `limit_req_zone $binary_remote_addr` effectively shares one bucket for all clients:
  one noisy client can consume the rate limit and cause 429s for legitimate users.

**Suggested fix**

In the `http` block of `nginx.conf`:

```nginx
set_real_ip_from 127.0.0.1;
set_real_ip_from ::1;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

Confirm that Tailscale Funnel sends `X-Forwarded-For` before applying; validate with a
temporary `$http_x_forwarded_for` field in the log format.

**Verification**

- New `access.log` lines show real public/LAN IPs instead of `172.18.0.1`;
- `curl` from an external network appears with its own IP.

## OPS-05 — Disk pressure: images, logs, rotation

**Evidence**

```
/dev/mmcblk0p2   58G   41G   16G   73% /
docker system df: Images 292  32.71 GB  (27.58 GB reclaimable, 84%)
-rw-r--r-- 1 pi pi 181M access.log   (first line 24/Jun/2026)
no logrotate rule for nginx
journal: 74.1 MB
```

**Impact**

16 GB free is enough for now, but the log grows unbounded (no rotation) and any large
deploy/image pull can fill the microSD.

**Suggested fix**

1. `docker image prune -a` (verify no needed tags first) — frees most of 27.58 GB.
2. Add `/etc/logrotate.d/nginx-smart-home` for
   `/home/pi/smart-home-prod/data/nginx/logs/*.log` (`weekly`, `rotate 8`, `compress`,
   `copytruncate`, `notifempty`).
3. Optional: cap journald (`SystemMaxUse=200M`) in `journald.conf`.

**Verification**

- `df -h /` below 50 %;
- `du -h access.log` stays bounded after rotation;
- `logrotate -d /etc/logrotate.d/nginx-smart-home` parses without errors.

## OPS-06 — zram failed, swap on microSD

**Evidence**

```
$ systemctl --failed
● rpi-zram-writeback.service      failed
● systemd-zram-setup@zram0.service failed

Nov 01..06 14:29  systemd[1]: Failed to start rpi-zram-writeback.service
free -m: Swp 3071 total, 186 used
```

The root filesystem is on the microSD (`/dev/mmcblk0p2`), so swap traffic wears the card.

**Suggested fix**

- Fix or mask the zram units (`systemctl status systemd-zram-setup@zram0.service`,
  `journalctl -u rpi-zram-writeback.service`), and/or
- move root/swap to the NVMe/SSD, reduce `vm.swappiness`, and consider `log2ram`.

**Verification**

- `systemctl --failed` is empty;
- `swapon --show` lists zram (or a disk not on the microSD);
- `vcgencmd measure_temp` and `iostat` stay stable.

## OPS-07 — MELCloud timeouts at the same time every day

**Evidence**

`ac-service`, 15 × `ERROR: Error getting state: The read operation timed out` in 7 days:

```
2026-11-05 01:05:40 .. 01:08:40   (5 consecutive minutes)
2026-11-06 01:05:42 .. 01:09:42   (+ 06:20:07)
2026-11-07 01:05:39 .. 01:08:39
```

**Impact**

Cloud state is stale during that window; local Zigbee control is unaffected. The
recurring minute suggests a MELCloud-side maintenance window or rate limiting.

**Suggested fix**

- Increase the MELCloud read timeout and add exponential backoff;
- suppress repeated errors in the 01:00–01:15 window (log once per window);
- consider backing off polling when the local Zigbee state is fresh.

**Verification**

- `docker logs ac-service` shows at most one warning per window instead of 4–5 errors.

## OPS-10 — SSH hardening

**Evidence**

```
$ sshd -T
passwordauthentication yes
permitrootlogin without-password
pubkeyauthentication yes

authorized_keys: ssh-rsa ... acmls@EgnalPC   (single key)
no ufw installed
0 failed password attempts in 30 days (persistent journal)
```

SSH listens on `0.0.0.0:22` and `[::]:22`. The workstation previously reached the Pi via
a global IPv6 address in the same /64 (LAN), so this does not prove inbound Internet
exposure, but there is no host firewall enforcing it.

**Suggested fix**

- `PasswordAuthentication no` in `/etc/ssh/sshd_config.d/`;
- install a firewall (ufw/nftables) allowing 22 only from LAN + tailnet;
- keep the single-key policy and review keys periodically.

**Verification**

- `sshd -T | grep passwordauthentication` returns `no`;
- `ufw status` shows the restrictive rules.

## Known false positives — do not re-report

1. **`casita-suenos` "5,728 errors"** — every line is an INFO Telegram long-poll
   (`getUpdates?timeout=30`). The word `timeout` trips naive greps.
2. **`zigbee2mqtt` "1,056 errors"** — debug JSON contains `"timeout":10000`.
3. **`401`/`403` matches in backend logs** — they are milliseconds inside timestamps
   (e.g. `23:12:20,403`), not HTTP statuses.
4. **Backend "restarted" 19 h ago** — deploy on 2026-11-06 13:34 UTC;
   `Restarts=0`, `OOMKilled=false`, `ExitCode=0`.
5. **`database.db is not a database`** — zigbee2mqtt 1.40 stores NDJSON, not SQLite;
   the file is fine and rewritten hourly.
6. **Immich ML missing** — may be a deliberate RAM optimisation (`profiles: [ml]`);
   see OPS-03.
7. **40 % CPU in `docker stats`** — first-sample artifact; a second sample shows <1 %.
